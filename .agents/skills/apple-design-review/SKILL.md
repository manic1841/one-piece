# Apple 設計審查

用 Apple 的判準看畫面。這是**只讀分析**：產出觀察與建議，不動程式碼；使用者確認後才另開實作。

Apple 的價值不是裝飾清單，而是三個可驗證的承諾：

- **Clarity（清晰）**——一眼看懂這是什麼、下一步是什麼。
- **Deference（內容優先）**——介面退讓，資料與任務在前。
- **Depth（層次）**——用空間、材質、順序表達深度，而不是加框、加陰影、加顏色。

三個承諾展開成五條可檢查的原則：**內容永遠比介面重要**、**一個畫面只做一件事**、**視覺層級極度重要**、**動畫要有意義**、**好設計是刪掉 100 次後剩下的東西**。

判準的來源是 Apple 自己的 HIG 語言與 WWDC《Designing Fluid Interfaces》：介面要**退讓、可預測、即時回應、可被中斷**。任何「看起來很酷但答不出目的」的東西都預設有罪。

## 使用時機

- 「用 Apple 的標準看這個頁面」
- 「這頁為什麼看起來亂 / 業餘 / 像 generic SaaS」
- 檢查單一畫面的視覺層級、動作密度、動態是否合理
- 元件或 UI diff 的設計品質審查

不適用：純 a11y 稽核、純 design token 一致性、純程式結構（那走 code-review）。

## 0. 找專案自己的規範

先搜尋專案是否已有 UI 契約（常見位置：`docs/ui/`、`DESIGN.md`、`CONTRIBUTING.md`、design system 目錄、Tailwind 設定、token 檔）。

- **有契約 → 契約優先。**Apple 原則是判準，專案文件是規格；衝突時以文件為準（若契約本身違反原則，另開一段記錄，不要直接判定文件錯）。
- **沒有契約 → 用現有程式碼與 token 反推既有慣例**，建議值一律落回既有級距。
- 有 `/gallery`、`/storybook`、類似樣板路由時先看它，用它的組合方式當基準。

## 1. 建事實底稿（不做評價）

先把畫面上實際存在的東西列出來，避免憑印象批評：

- 區塊順序與各自的任務
- 一級視覺元素（最大字、最大間距、唯一的色塊、主動作）
- 動作數量與位置（主／次／破壞性）
- 動態：哪裡動、動什麼屬性、什麼曲線、能不能被中斷
- 資訊分層：第一層／收合／進階

看得到渲染結果就用瀏覽器實際開；只能讀程式碼時**開頭標註「未看渲染結果」**並調降版面類結論的信心。

## 2. 逐條套原則

一次一條，每條先問「這裡成立嗎」，再寫證據（元素、行號、截圖位置）。

**內容 > 介面**

- 外框、分隔線、圖示、標題列是否吃掉視線？拿掉後層級還清楚嗎？
- 有沒有為 UI 存在而存在的東西（空 Card、純裝飾眉標、與標題重複的說明）？
- 空白是拿來呼吸，還是拿來填滿？

**一畫面一件事**

- 這頁用一句話說得出來嗎？說不出來就是兩頁。
- 有沒有互不相干的主要動作在搶主位？
- 次要任務是否收進 disclosure／detail／sheet。

**視覺層級**

- 三秒鐘能排出 1→2→3 嗎？排不出來就是層級失效。
- 對比是否靠**尺寸、字重、間距、位置**建立，而不是只靠顏色？
- 同層級的元件長得一樣嗎（containment、對齊、動作位置）？
- 數字有沒有被當成裝飾放大，而決策資訊被壓縮？
- 主要動作是不是只有一個，且在最不需要找的位置？

**動態**

- 每個動畫回答什麼問題（回饋？空間關係？狀態切換？）答不出來就刪。
- 回饋在按下瞬間嗎？可逆轉換的 easing 對稱嗎？動畫期間輸入被鎖住嗎？
- 進場動畫有沒有超過必要的長度、或用 `@keyframes` 卡住可被中斷的互動？

**刪除**

- 逐元素問：拿掉它，使用者會少做對一件事嗎？不會 → 標為可刪。
- 對每個建議再問一次「這是加法還是減法」；加法要能說出被它取代掉什麼。

## 3. 排序與表達

依「影響 × 改動成本」排序，分三級：

| 級別     | 意義                                               |
| -------- | -------------------------------------------------- |
| **必修** | 違反專案契約，或使用者會做錯事                     |
| **該修** | 原則失效但可用（層級、密度、無意義動態、動作競爭） |
| **可刪** | 純減法：拿掉更清楚                                 |

每條固定四欄，沒有證據的條目不要寫：

| 位置 | 原則 | 觀察（有事實） | 建議（具體到能動手） |
| ---- | ---- | -------------- | -------------------- |

建議要給到可執行粒度：拿掉哪個框、合併哪兩個標題、把哪個動作降到 secondary、字級從哪一階降到哪一階、動畫改成哪個既有 token。**不要寫「可以再精簡」這種沒有落點的建議。**

最後補兩段：

- **一句話診斷**：這頁最傷 Clarity 的一件事。
- **不要動的地方**：已經做對、改了反而變差的（避免照著建議一路拆壞）。

## 規則

- 契約優先；無契約時序取捨：內容 > 結構 > 空間 > 顏色 > 動態，仍不明確就選**裝飾較少、新元素較少**的做法。
- 建議值只落在專案既有級距；需要新模式時明講「這是新模式，要另開設計決定」。
- 不把「加」當成解法：新增區塊一定同時指出它取代了什麼。
- 顏色只用來編碼狀態分類，不用來裝飾。
- 一次聚焦單一畫面；跨頁一致性放到最後一段，別混進主表。
- 輸出語言跟隨使用者（預設繁體中文），用語直白、技術性，不客套。
