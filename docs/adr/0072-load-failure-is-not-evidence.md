# 載入失敗不是證據：資料未知即未就緒

**日期：** 2026-09-29
**狀態：** 已接受
**規範來源：** [monthly-close.md](../monthly-close.md) §3（UI 組構：大一統步驟 registry、關帳前的載入失敗語意）

關帳階段顯示的資料幾乎全部來自載入（prefill 草稿、evidence 清單、報表 bundle）。載入失敗時畫面原本渲染成空草稿／空清單，與「本月乾淨、無事可做」在視覺上完全無法區分——使用者會看到一個看似正常的階段並確認它。本 ADR 定調：**載入失敗代表資料 UNKNOWN，不是 EMPTY**；該階段顯示自己的罐頭錯誤訊息，且所有讀這份資料的把關一律將 UNKNOWN 視為未就緒。細部契約（錯誤文案歸屬、`CloseStageLoadError` 的呈現位置、prefill 的例外）見 `規範來源`。

## 把關與 prefill 的差別

- **把關（gate）**：Completeness Check 的就緒狀態、Financial Reports 的 Generate 守門、Close Period 的 drift 把關都讀載入資料。資料 UNKNOWN 時視為未就緒——「還沒檢查」與「檢查通過」必須是不同狀態，否則失敗會被當成通過。
- **prefill**：prefill 只是便利，不是關卡。prefill 失敗**不阻擋確認**（使用者手打的草稿仍可提交），但**必須顯示錯誤**，否則畫面又回到「空白＝乾淨」的假象。代價是使用者可能誤以為本月沒有前期資料；以可見的錯誤訊息承擔，優於讓錯誤默默變成空值。

## 失敗時顯示什麼

同一期間的**重新載入失敗保留上一輪已載入的資料**（畫面上是最後已知值，不是空白），並顯示錯誤；期間切換的載入失敗則沒有上一輪同月資料可留，畫面顯示錯誤與空值。因此「有沒有資料」不能單獨當作把關依據，把關一律以「已知且未失敗」為讀法（具名實作見 `規範來源` 的 §3）。理由是兩種失敗的語意不同：切月失敗代表「這個月的資料未知」（空是誠實的），同月刷新失敗代表「已知值可能已過時」（清空反而製造新的假象）。

## Considered Options

- **失敗即渲染空值（維持現況）**：否決。空值與「乾淨」不可區分，失敗被靜默解讀為通過，這是本 ADR 要消滅的失敗模式。
- **任何載入失敗都阻擋確認**：否決。把便利（prefill）升格成關卡，會讓一次網路抖動鎖死一個使用者已能正確填寫的階段；把關只該讀真正作為證據的資料。
- **重新載入失敗時清空為 null**：否決。丟掉最後已知值會讓 drift 與就緒判定誤報，且畫面上的資訊比失敗前更少。
- **在後端／application 層統一攔截載入失敗**：否決。載入失敗是呈現層的狀態問題（每個階段自載自己的資料），後端攔截既看不到 UI 的已知值，也無法決定「顯示錯誤但仍可確認」這種分級語意。

## Revisit When

階段資料改為本機快取／離線可用（UNKNOWN 變成可恢復的暫態），或載入失敗能細到欄位層級（部分未知而非整份未知）時，本 ADR 的二元判定需重新設計。
