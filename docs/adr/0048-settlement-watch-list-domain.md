# 監看清單是獨立 domain,記帳完整性檢查作為結算流程的軟關卡

## 狀態

已接受(2026-09)

## 背景與動機

每月專案結算前,使用者需要確認每筆記帳都確實記錄成功。經設計訪談釐清,真正的
缺口是**記帳完整性**(怕自己漏記),不是寫入可靠性——建立交易走 Firestore
`runTransaction` 原子寫入(見 ADR-0038、ADR-0039),畫面顯示成功即已落庫。

系統無法直接看到「沒被記下來的事」,必須以既有資料推斷。因為分配(Allocation)
是可選的,「監看專案當月零分配」可能是真的沒花錢,也可能是花了但忘了記錄或忘了
分配——系統無法自動區分,這正是需要人工確認的原因。

## 決策

1. **監看清單(Watch List)是獨立 domain**,不是專案旗標、不是設定集合的延伸。
   使用者明標記參與檢查的對象;對象類型包含專案、會計科目(LedgerCode)與債務
   帳戶。未標記的對象不參與檢查,避免季節性或已還清的專案造成長期叨擾。
   曾考慮在專案文件加 `isSettlementWatched` 旗標:實作最精簡,但會把一個獨立
   domain 的管理拆散在多個既有實體上,且無法表達「監看 ledger code / 債務」,
   故不採。
2. **還債用自己的檢查類型,不監看負債科目**。還債分錄的借方使用債務的
   `linkedLedgerCode`,監看該科目時,當月新借款入帳會讓活動不為零,**掩蓋漏還**
   ——盲點正好出現在最需要提醒的月份。因此債務檢查語意為:啟用中、在借款期間
   內的債務,目標月沒有任何 `DEBT_PAYMENT` 交易即警示(可重用
   `hasDebtPaymentForAccount`)。
3. **檢查是結算流程的軟關卡,且異常才出現**。在結算對話框的選擇步驟自動執行;
   所有監看對象活動正常時零點擊、零摘要直接進預覽;有異常才內嵌警示,需逐項
   「確認無漏記」才放行。確認狀態不持久化:生命週期與單次結算對話框 session
   吻合,已結算月份重新檢查是可接受的代價。曾考慮每家庭 × 每月的確認紀錄集合:
   需新集合與規則,等重複叨擾真實發生再升級,故不採。
4. **檢查只讀不寫**。檢查是監看清單的衍生行為,依既有 repository
   (`getAllocationsByMonth`、`listByDateRange` + 交易上的 `ledgerCodes`
   反正規化陣列、`hasDebtPaymentForAccount`)在記憶體中計數,不新增寫入路徑、
   不修改任何交易。第一版只做零活動判定;歷史偏離(比對前 3-6 個月均值)等
   零活動上線累積體感後再評估。

## 影響

- 新增監看清單 domain:資料模型、設定頁家庭區的監看清單管理卡片,與結算選擇
  步驟的完整性檢查(對話框與全頁兩個結算入口共用同一檢查 use case)。
- 「家庭分類」與「媽媽專案」是互相獨立的維度(見 CONTEXT.md),完整性檢查只看
  監看清單,不對兩者做交叉比對;從記帳表單移除「家庭」分類屬於另一項變更,
  不在本決策範圍。
- 推播通知、開 App 橫幅、Dashboard 卡片等被動提醒位置皆不在第一版範圍;
  檢查時機貼著結算動作,誤報成本最低。
