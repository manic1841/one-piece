# 監看清單是獨立 domain,記帳完整性檢查作為結算流程的軟關卡

**狀態：** 已接受（2026-09）
**規範來源：** [monthly-close.md](../monthly-close.md) §4；[debt-accounts.md](../debt-accounts.md) §5.5；[data-structure.md](../data-structure.md) §watchList

每月專案結算前,使用者需要確認每筆記帳都確實記錄成功。經設計訪談釐清,真正的缺口是**記帳完整性**(怕自己漏記),不是寫入可靠性——建立交易走 Firestore `runTransaction` 原子寫入(見 [ADR-0038](0038-command-atomicity-and-retry-policy.md)、[ADR-0039](0039-allocation-atomicity-and-identity.md)),畫面顯示成功即已落庫。

系統無法直接看到「沒被記下來的事」,必須以既有資料推斷。因為分配(Allocation)是可選的,「監看專案當月零分配」可能是真的沒花錢,也可能是花了但忘了記錄或忘了分配——系統無法自動區分,這正是需要人工確認的原因。因此把監看清單做成**獨立 domain**(而不是專案旗標或設定集合的延伸),並把檢查做成結算流程的**軟關卡**:只讀不寫、異常才出現、確認狀態不持久化。

## Considered Options

- **在專案文件加 `isSettlementWatched` 旗標**:實作最精簡,但會把一個獨立 domain 的管理拆散在多個既有實體上,且無法表達「監看 ledger code / 債務」,不採。
- **監看債務的負債科目**:還債分錄的借方使用債務的 `linkedLedgerCode`,監看該科目時,當月新借款入帳會讓活動不為零,**掩蓋漏還**——盲點正好出現在最需要提醒的月份。改用「啟用中、在借款期間內的債務,目標月沒有任何 `DEBT_PAYMENT` 交易即警示」,並重用既有的 `listDebtPaymentsByDateRange`(一次查詢涵蓋所有債務)以避免 N+1、同時取得筆數與金額摘要。
- **每家庭 × 每月的確認紀錄集合**:需新集合與規則;確認狀態不持久化,等重複叨擾真實發生再升級。
- **第一版就做歷史偏離偵測(比對前 3-6 個月均值)**:零活動上線累積體感後再評估。

## Consequences

- 新增監看清單 domain:資料模型、設定頁家庭區的監看清單管理卡片,與結算選擇步驟的完整性檢查(對話框與全頁兩個結算入口共用同一檢查 use case)。
- 檢查時機貼著結算動作,誤報成本最低;推播通知、開 App 橫幅、Dashboard 卡片等被動提醒位置皆不在第一版範圍。
- 「家庭分類」與「媽媽專案」是互相獨立的維度(見 `CONTEXT.md`),完整性檢查只看監看清單,不對兩者做交叉比對;從記帳表單移除「家庭」分類屬於另一項變更,不在本決策範圍。
