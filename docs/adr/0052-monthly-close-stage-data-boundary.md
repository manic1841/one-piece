# 關帳工作流階段資料建立邊界：階段確認冪等建立該階段資料

**狀態：** 已接受
**規範來源：** [monthly-close.md](../monthly-close.md)；[ui/visual-standards.md](../ui/visual-standards.md) §帳戶餘額階段排版

Monthly Close 以階段表達關帳進度，每個階段完成由使用者確認；確認動作＝冪等執行該階段的資料建立（已存在不重複）＋標記階段完成，輸入隨確認一次提交，不做跨階段的一鍵全部快照。取捨是使用者在每個階段都要按一次確認，比一鍵慢；但單一階段的輸入錯誤不會被跨階段的大量寫入掩蓋，且每個階段的冪等鍵讓重複確認安全。

**修訂（證券買入／賣出 diff-merge）**：證券買入／賣出階段從「刪除重建」改為 diff-merge（載入列以文件 ID 更新、新增列建立、移除列刪除），並列為可重確認階段（與帳戶餘額同）。原刪除重建會在每次重新確認時換掉所有文件 ID，破壞下個月 prefill 的載入對應，也讓使用者在 pipeline 上失去「這批列是哪次確認產生」的可追蹤性。取捨是寫入路徑多出 update 與 delete 分支（比純 create 慢、多一層意圖判斷）；但重複確認不再重複入帳，既有列的 ID 穩定，且刪除範圍由呼叫端明確提供（`removedTransactionIds`），不誤刪監看清單外的手動交易。手動交易**會被 prefill 載入為階段列**：使用者刪除或編輯後，該文件即轉為階段管理——「不受影響」只保證到使用者主動操作前。債務還款階段維持原有原子邊界，不納入此修訂。

單段式（確認即建立）優於兩段式（輸入提交與階段確認分離）：兩段式會產生「階段 PENDING 但資料已存在」的中間狀態，確認補齊邏輯可能覆蓋已提交資料（如 portfolio 補零覆蓋 deposits/withdrawals），且 UI 需多處理一個子狀態。輸入驗證提前由 UI 表單 inline 檢查承擔，不需提前建資料。工作流內建立的是既有合法事件（快照與交易），關帳工作流與期間狀態本身不是財務事件（[ADR-0050](0050-financial-period-workflow-state.md)）。

## Considered Options

- 一鍵建立全部快照（跨階段）：會掩蓋單一階段的輸入錯誤，拒絕；逐階段確認、該階段建立該階段資料。
- 兩段式（輸入提交先建立、階段確認補齊快照）：產生「階段 PENDING 但資料已存在」的中間狀態，補齊邏輯可能覆蓋已提交資料，拒絕；單段式冪等建立。
- 獨立 Account Reconciliation 階段：財務報表已呈現現金一致性（ADR-0020、ADR-0051），獨立階段重複同一檢查，移除。
- 寫入時驗證涵蓋、不新增關帳階段：驗證已在寫入邊界強制，但關帳需要明確的驗證步驟與 unresolved exceptions 路由，拒絕；新增僅驗證的 TRANSACTION_VALIDATION 階段。
- 股東往來延後擴充、不加關帳入口：UI 規格要求關帳時能建立 FINANCING intent 交易，拒絕；投資與融資輸入一次到位。
- 還款保留在 Transaction form 作為平行路徑：月度還款集中到關帳工作流以維持單一入口，月中臨時還款於關帳時一次輸入，拒絕平行路徑。
- 缺漏輸入時阻擋確認按鈕：違反單段式冪等確認的提交邊界（確認不為未輸入帳戶偽造零值，也不阻擋已輸入部分先行確認），拒絕。
- 期間顯示合併進 `YearMonthPicker`（readonly mode）：picker 是 9 個呼叫點的全站共用元件，只為月度關帳加展示模式會讓全部呼叫點共同承擔單一頁面需求，拒絕；獨立 `PeriodBadge` 展示元件承擔。
- 維持只送 `amount`：外幣與持倉只在畫面上算、不落庫，下個月證券將沒有上月持倉可匯入，同一批快照也因寫入來源不同而完整度不一致，拒絕；確認時一次落庫。
- Market Value 讓使用者另外輸入：會造成 Holdings Value ≠ Market Value 的不一致，拒絕；由系統計算。
- 證券買入／賣出重確認維持刪除重建：重複確認時換掉所有文件 ID，下個月 prefill 無法對應既有列，且使用者的編輯歷史在 pipeline 上不可追蹤，拒絕；改為 diff-merge（ID 更新既有列、建立新增列、刪除移除列）。
- Diff-merge 刪除範圍由 repository 推斷（比對當月既有交易與提交列）：隱式推斷可能誤刪監看清單外的手動交易，拒絕；由呼叫端明確提供 `removedTransactionIds`。
