# 開放使用者自建 LedgerCode

**狀態：** 已接受（2026-09）

## 背景與動機

家庭財務會隨人生階段改變，系統預設科目無法覆蓋所有情境（買房後需要區分各筆不動產、生小孩後需要 `expense:child`、接案收入需要 `income:freelance`）。使用者因此需要自建科目，但又不能破壞既有分類結構，所以自建範圍與校驗規則必須明確定義。

收斂前的世界有一處分歧：資料契約（`CustomLedgerCodeCreateSchema.code`）接受任何深度的自由字串，ADR-0022 也早已為不動產、薪資、獎金加上 `userSelect` 與允許前綴，讓這些意圖的使用者去挑具體科目；然而建立表單只能產生二層碼，於是 `asset:property` 底下的選單永遠只有一個選項，`userSelect` 形同空轉。缺口在建立入口，不在資料契約。

## 決策

1. **自建範圍是 category 與明細科目**：使用者可在既有類型前綴下新增 category（`type:category`），也可在既有 category 下新增明細科目（`type:category:detail`）。類型前綴不可變更；已有分錄引用的科目不可修改。明細科目的 parent 必須存在、必須是 category、且必須啟用中。
2. **拒絕比明細更深的自建**：明細科目不可再往下細分。被否決的方案有二：「自由字串、深度不限」讓使用者建立任意深度的科目，報表分組與標籤解析都要處理無界深度，換不到實際情境；「完全不開放明細」則會讓 ADR-0022 的 `userSelect` 永遠空轉，必須連帶改寫 ADR-0021。
3. **自訂科目的生命週期只有啟用與停用**：不提供刪除。被否決的方案是提供刪除——刪除要處理分錄、分配模板與監看清單等引用面，而停用已能達到「不再出現在新交易」的效果。停用 category 前必須先停用其明細科目，避免留下「parent 已停用、明細仍可選」的狀態；反過來，停用中的 category 不可再掛新明細。
4. **既有二層自建不變**：本 ADR 原本就已定案二層自建，本次是把明細科目納入同一份自建契約，不是新增第二種自建模式。

## 影響

- 建立規則（合法碼形狀、深度上限、parent 條件、生命週期）住在 [data-structure.md](../data-structure.md) 的 `ledgerCodes` 章節；與意圖映射的搭配（哪個意圖讓使用者挑哪些科目）住在 [transaction-flow.md](../transaction-flow.md)。本 ADR 只保留決策與取捨。
- 「其他支出」與「其他收入」不再列出其他意圖已負責的系統科目，只列使用者自建的科目加上該意圖自己的預設碼；`expense:loan_interest` 補上專屬意圖，不再依賴模糊的前綴過濾。
- 未實作、另案追蹤：報表層對明細科目的父科目 roll-up 與標籤解析（issue #182）。
- 討論脈絡與實作見 issue #159。
