# 開放使用者自建 LedgerCode

**狀態：** 已接受（2026-09）
**規範來源：** [data-structure.md](../data-structure.md) §ledgerCodes；[transaction-flow.md](../transaction-flow.md)

家庭財務會隨人生階段改變，系統預設科目無法覆蓋所有情境，使用者因此需要自建科目，但又不能破壞既有分類結構，所以自建範圍與校驗規則必須明確定義。

自建範圍定為兩層：使用者可在類型前綴下新增 category，也可在既有 category 下新增明細科目；類型前綴不可變更，明細科目不可再往下細分，自訂科目只提供啟用與停用、不提供刪除。

收斂前資料契約接受任何深度的自由字串，建立表單卻只能產生二層碼，於是 `userSelect` 形同空轉——缺口在建立入口，不在資料契約。

## Considered Options

- **自由字串、深度不限**：報表分組與標籤解析都要處理無界深度，換不到實際情境。拒絕。
- **完全不開放明細科目**：會讓既有的 `userSelect` 永遠空轉。拒絕。
- **提供刪除**：刪除要處理分錄、分配模板與監看清單等引用面，而停用已能達到「不再出現在新交易」的效果。拒絕。

## Consequences

- 未實作、另案追蹤：報表層對明細科目的父科目 roll-up 與標籤解析（issue #182）。
- 討論脈絡與實作見 issue #159。
